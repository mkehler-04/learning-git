01

Repository (repo)

The project folder, tracked by Git and hosted on GitHub et al.

A repository is your project's files plus a hidden .git directory that stores every snapshot, branch and the complete history. A copy hosted on GitHub, GitLab or Bitbucket — a remote, usually called origin — is how a team shares that history.

Try it

git init
git remote add origin https://github.com/you/project.git
git status

Considerations

  • Add a .gitignore on day one so build output, node_modules and .env files never get committed.
  • Never commit secrets. History is permanent — deleting a file later doesn't remove it. Rotate any leaked key immediately.
  • Give hosted repos a README, a LICENSE and clear contribution notes.
  • Large binaries bloat every clone forever; use Git LFS for media and datasets.

02

Clone

Download a copy of the code to your machine.

git clone copies an entire repository — every file, commit and branch — onto your computer and automatically sets up a remote called origin pointing back to where it came from, so you can push and pull later.

Try it

git clone https://github.com/you/project.git
cd project
git remote -v   # shows origin

Considerations

  • HTTPS vs SSH: SSH keys avoid repeated credential prompts; HTTPS works through most corporate firewalls.
  • For huge repos, try a shallow clone (--depth 1) or a partial clone (--filter=blob:none).
  • Clone vs fork: if you can't push to the original, fork it on GitHub first, then clone your fork.
  • Avoid cloning into cloud-synced folders (OneDrive, Dropbox, iCloud) — sync clients can corrupt the .git folder.

03

Branch

A safe parallel timeline to the main codebase.

A branch is a lightweight, movable pointer to a commit. Creating one lets you build a feature or fix a bug in isolation while main stays stable. HEAD marks the branch you're currently on, and it moves forward with each new commit.

Try it

git switch -c feature/login   # create + switch
git branch                    # list branches
git switch main               # go back

Considerations

  • Keep branches short-lived and focused — long-running branches drift and cause painful conflicts.
  • Use descriptive names with prefixes such as feature/, fix/ or docs/.
  • Protect main with branch protection rules (required reviews, passing CI).
  • Delete branches once merged to keep the list readable.

04

Commit

A snapshot + message describing your changes.

You first stage changes with git add, then git commit records the staged snapshot together with an author, timestamp, parent commit and message. Each commit gets a unique SHA hash, like a1f9c2e, that identifies it forever.

Try it

git add login.js
git commit -m "feat: add login form"
git log --oneline

Considerations

  • Commit small, logical units — one idea per commit makes review, revert and bisect easy.
  • Write messages in the imperative: “Add login form”, not “stuff” or “fixed things”.
  • Use git add -p to stage only parts of a file.
  • Check what you're about to commit with git diff --staged.

05

Push / Pull

Upload to / download from the hosted repository.

git push sends your local commits up to the remote. git pull fetches commits others have pushed and integrates them into your current branch — it's a git fetch followed by a merge (or a rebase, if configured).

Try it

git push -u origin feature/login   # first push
git pull                           # get teammates' work
git fetch --all                    # look, don't integrate

Considerations

  • Pull before you start and before you push — it keeps conflicts small.
  • A push is rejected if the remote has commits you don't; pull first, then push.
  • Never --force push shared branches. If you must, use --force-with-lease.
  • Prefer linear history? git config --global pull.rebase true.

06

Diff

The visual difference between two versions of code.

A diff compares two versions line by line — your working files, the staging area, two commits or two branches. Removed lines are shown in red with a −, added lines in green with a +. It's how you review your own work and everyone else's.

Try it

git diff                     # unstaged changes
git diff --staged            # what you'll commit
git diff main..feature/login # branch vs branch

Considerations

  • Plain git diff only shows unstaged changes — add --staged to see what's queued.
  • --word-diff is much easier to read for prose and long lines.
  • Pure formatting changes can hide real ones; -w ignores whitespace. Keep reformatting in separate commits.
  • On GitHub, a PR's “Files changed” tab is a diff, and /compare diffs any two branches.

07

Merge

Combine a branch back into another branch.

git merge brings the history of one branch into the branch you're on. If both branches have new commits, Git creates a merge commit with two parents. If the target hasn't moved, Git simply fast-forwards the pointer.

Try it

git switch main
git merge feature/login
git branch -d feature/login   # tidy up

Considerations

  • Agree on a team strategy: merge commit, squash, or rebase-and-merge.
  • Merge commits preserve exactly when and how work came together; squash keeps main compact but loses individual commits.
  • Pull the latest target branch before merging.
  • Run the tests after a merge — two changes that work alone can break together.

08

Rebase

Replay your commits on top of the latest main.

git rebase lifts your branch's commits off their original base and re-applies them, one by one, on top of another branch. The result is a clean, linear history — but the replayed commits are new commits with new hashes (X → X′).

Try it

git fetch origin
git rebase origin/main
git rebase -i HEAD~3   # squash / reorder / reword

Considerations

  • Golden rule: never rebase commits other people have already pulled.
  • Because hashes change, pushing a rebased branch needs --force-with-lease.
  • Interactive rebase (-i) is great for cleaning up a branch before opening a PR.
  • Stuck? git rebase --abort undoes it, and git reflog can find any lost commit.

09

Merge conflict

Two changes touched the same lines; you choose.

When two branches change the same lines differently, Git can't know which is right, so it pauses and writes both versions into the file between conflict markers. You edit the file to the result you want, remove the markers, stage it and continue.

Try it

git status                # lists conflicted files
# edit file, delete <<<<<<< ======= >>>>>>>
git add page.js
git commit                # or: git rebase --continue

Considerations

  • Don't panic — git merge --abort returns you to where you started.
  • Make sure every <<<<<<<, ======= and >>>>>>> marker is gone before committing.
  • Small, frequent merges mean small, easy conflicts.
  • Use a merge tool — VS Code has a built-in 3-way merge editor. git rerere can remember repeated resolutions.

10

Pull Request (PR)

"Please review and merge my branch."

A pull request is a GitHub feature (GitLab calls it a merge request), not a Git command. It proposes merging your branch into another, and gives the team one place for the diff, discussion, code review and automated CI checks before anything lands on main.

Try it

git push -u origin feature/login
gh pr create --fill          # GitHub CLI
gh pr merge --squash

Considerations

  • Keep PRs small and focused — reviewers catch more in 200 lines than in 2,000.
  • Explain the what, the why and how to test; add screenshots for UI changes.
  • Write Fixes #17 in the description to link and auto-close an issue.
  • Open a draft PR for early feedback; require passing CI and approval before merging.

11

Issue

A ticket: bug, feature, or task.

Issues track work that needs doing. Each has a title, description, labels, assignees and optional milestones, and can be linked to the pull requests that resolve it. When a linked PR merges, the issue closes automatically.

Try it

gh issue create --title "Login button unresponsive" --label bug
gh issue list --assignee @me
git commit -m "Fix click handler (fixes #17)"

Considerations

  • Good bug reports include steps to reproduce, expected vs actual behaviour and environment details.
  • Use issue templates and consistent labels so reports are easy to triage.
  • Search before filing to avoid duplicates.
  • Break large work into smaller issues and track them on a GitHub Project board.
